## General overview

### The approach in everyday terms

Deserts of Kharak loads definitions describing its units, weapons, research,
factions and visual assets. A runtime mod enters the loading process and supplies
modified definitions or replacement assets before the game uses them.

Our implementation has two main pieces:

1. **A loader and DLL patch.** These arrange for a small set of our functions to
   run at important points in the game's loading and playback code.
2. **Content and rules.** These define the cruiser transfer, its research, repair,
   health, appearance and selected voice responses.

The game's original executable, managed assemblies and asset archives remain
unchanged on disk. The installed mod adds its own files beside the game. Its
managed hooks are applied in memory when the game starts.

This distinction makes the approach reversible, but it does not make every game
system automatically extensible. The work is identifying the relevant systems,
changing all their related definitions consistently, and surviving transitions
between menus, matches and the campaign.

### What already works

The current mod moves the Assault Cruiser from Coalition/Soban to Khaaneph,
replacing the Honor Guard slot. It also installs a custom Khaaneph model.

| Capability | What has actually been demonstrated |
|---|---|
| Change faction rosters | Coalition and Soban lose Assault Cruiser production; the Khaaneph carrier produces the transferred unit. |
| Change research progression | Sandskimmer fabrication leads to Assault Ship fabrication, then Assault Cruiser fabrication. |
| Change health and repair | The cruiser has 3650 HP and native Khaaneph passive repair instead of active self-repair. |
| Preserve a research-dependent weapon | The anti-air upgrade enables the existing cruiser's air weapon. |
| Replace unit geometry | A custom angular hull, forward jaw armor, bridge and retained Assault weapons appear in the game. |
| Preserve moving parts | Native missile-door, cannon-recoil and steering animations deform the new model in a live test. |
| Change selected voice responses | Standard command, production and research responses use existing Khaaneph recordings. |
| Keep changes across reloads | Research and the textured preview survive repeated match/menu cycles. |
| Separate campaign registration | Entering SinglePlayer registration restores the original Coalition research, production and Assault health. A full campaign mission was not tested. |

![The custom Assault Cruiser rendered by a native game camera](../example/evidence/models/game-match-round-0.png)

*A capture from the game, rather than a Blender presentation render. The custom
model retains native weapon and suspension bindings.*

These are useful building blocks for modding. They do **not** yet constitute a
general editor or demonstrate adding a fifth independent faction.

### What a future modding environment could offer

**HYPOTHESIS.** A shared modding environment could put the difficult integration
work behind reusable tools. Mod authors could work with understandable unit and
faction definitions, asset files and validation reports rather than editing
machine instructions for every change.

For a human author, the intended workflow would look like this:

1. Create a mod folder and give it a unique identity.
2. Choose existing unit templates or supply new content.
3. Edit a roster, research tree, statistics and abilities.
4. Import models, textures, sounds or effects through supported tools.
5. Run validation to catch broken references and missing bindings.
6. Launch a test match and inspect useful diagnostics.
7. Package the mod and declare its dependencies and compatible game build.

Such an environment would have three audiences: players installing mods, content
authors creating them, and programmers extending the environment itself. A good
editor would expose ordinary concepts such as “health” and “fabrication
prerequisite”; private engine field names would remain implementation details.

### What remains difficult

| Goal | Current assessment |
|---|---|
| More balance, roster and research changes | High confidence, using the demonstrated approach. Each change still needs its own validation. |
| More models using existing unit rigs | High confidence. Export and binding tools need to become general rather than cruiser-specific. |
| External recordings and new audio events | Feasible-looking, but external audio import and completely new dialogue hierarchies are not implemented. |
| New particle effects and projectile visuals | Clear integration points exist in inspected code; custom content has not been demonstrated end to end. |
| Additional selectable factions | The largest unresolved content extension. Selection, saved customization, loadouts, AI and previews must agree. |
| Entirely new gameplay mechanics | Depends on the mechanic. Data-driven variations are easier than adding new simulation behavior. |
| Reliable multiplayer mod combinations | Requires deterministic behavior, compatible definitions and real peer testing. |

The strongest next experiment would be one additional faction, selectable beside
all four existing factions, with its own roster, research, preview and functioning
AI. It should survive repeated matches before anyone promises a public faction SDK.

A useful modding layer is therefore a credible goal. The existing work establishes
a foundation; a polished environment remains a separate engineering project.

## Part I — Proven concepts: how the current mod works

This part documents the actual 1.1.0 implementation. The techniques are proven
within the stated scope, but some helpers intentionally contain assumptions
specific to this unit and game build.

### I.1 Scope and result

**PROVEN — runtime and source/data.** The supported executable is the 64-bit
Windows Steam build identified above. The game runs Unity 5.2.2f1 with Mono.
The package version is **1.1.0**; the runtime and patcher assembly identities
remain **1.0.0.0** for the existing hook ABI. Those are different version numbers
with different purposes.

The mod targets Skirmish, AISkirmish and Multiplayer registration. The native
end-to-end tests exercised offline AI skirmishes. Multiplayer mode recognition
exists in code, but a real network peer session has not been verified.

Three identifiers are essential to understanding the transfer:

| Role | Internal key | Treatment |
|---|---|---|
| Original Assault Cruiser | `G_Battlecruiser_MP` | Donor for the transferred unit; removed from Coalition producers. |
| Soban Assault Cruiser | `C_Sob_AssaultCruiser_MP` | Removed from Soban producers. |
| Khaaneph Honor Guard slot | `K_HonorGuard_MP` | Retained as the backend key, with Assault behavior and the custom model. |

The `G_` prefix does not establish who can build the unit. In this installation,
`G_Battlecruiser_MP` is the Coalition-owned Assault Cruiser. The ordinary Coalition
Battlecruiser, `C_Battlecruiser_MP`, is a different unit and is preserved.

Keeping the Khaaneph backend key preserves existing DLC replacement and HUD
connections. It does not mean the visible cruiser still uses Honor Guard
mechanics. Conversely, this is **replacement within an existing slot**, not proof
of registering a completely new playable unit or faction.

**Implementation:** [Runtime.cs](../example/src/Runtime.cs), especially `PrepareTransfer`,
`ApplyTransfer`, `PatchProducers` and `PatchTechAssets`.

### I.2 Loader and managed hooks

**PROVEN — runtime.** Unity Doorstop loads the BepInEx 5.4.23.4 preloader. Our
preloader plugin uses Mono.Cecil to add calls to the game's managed code before
the target assembly is loaded for execution.

The release patch targets `BBI.Unity.Game.dll`. It checks that file's SHA256 before
adding hooks and rejects a second application of the same runtime patch.

```text
Game starts
  -> Doorstop loads BepInEx preloader
  -> patcher checks the original managed assembly
  -> Cecil inserts managed calls in memory
  -> game executes with those calls present
  -> runtime prepares content at the relevant loading boundaries
```

The release hooks are deliberately limited:

| Native site | Hook purpose |
|---|---|
| `ShipbreakersMain.InitializeEntityManager` | Prepare current assets before registration; register and audit supplemental definitions afterward. |
| `PlayerCustomizationPanel.ContentManager.SceneContent.SetFactionPack` | Prepare the current preview pack before native preview instantiation. |
| `AudioAssetBundleLoader.LoadAssetBundle(StreamableAssetContainer)` | Load the original Assault dialogue hierarchy alongside Khaaneph speech. |
| `VOController.ExecuteVO` | Clone and route relevant Khaaneph Assault events through that hierarchy. |
| `AudioAssetBundleLoader.TryLoadClip` | Substitute approved Khaaneph recordings at clip lookup. |
| `GameLocalizationManager.GetEntry(string)` | Resolve the mod's additional description keys. |

The original general BepInEx chainloader crashed in its `ThreadingHelper`
initialization on this installation. The working release removes that built-in
chainloader entry and relies on direct static hooks. It does not add a new mod
MonoBehaviour or rewrite `UnityEngine.dll`.

This is a compatibility finding for the tested setup, not a claim that every
BepInEx plugin or MonoBehaviour is impossible on every Unity 5.2 game.

**Implementation:** [Patcher.cs](../example/src/Patcher.cs). The static verifier checks
method signatures, hook ABI, every registration return, serialized IL,
duplicate/unsupported-build rejection and old-Mono metadata.

### I.3 Asset cloning and registration

**PROVEN — runtime.** A unit is a collection of connected definitions. The mod
copies the donor's unit container fields, then substitutes independent versions
of the data that must change: unit attributes, HUD, view and selected abilities.

`DataPlan.Clone` recursively copies relevant managed `BBI.*` data and arrays while
preserving references to Unity objects. `CloneAsset` separately clones a
`ScriptableObject`, copies its managed fields and invokes its initialization.
That distinction matters: a copied wrapper can otherwise continue referencing
shared mutable data or lack prepared nonserialized fields.

For example, the following is a shortened excerpt from the real transfer logic,
executed inside `Runtime`; it is **not** a standalone SDK API:

```csharp
ScriptableObject attributes = CloneAsset(
    (ScriptableObject)Reflect.Get(Source, "m_Attributes"),
    "K_AssaultCruiser_UnitAttributes_MP");

Reflect.Set(Reflect.Get(attributes, "m_Attributes"),
    "m_MaxHealth", AssaultHP);

TransferredFields["m_Attributes"] = attributes;
```

The native `AssetContainer` caches the flattened attribute list in `mDataCache`.
After changing a unit's contained assets, the mod clears that cache and calls
`OnEnable` again. Changing a serialized reference without rebuilding the cache
can leave registration consuming old data.

The command panel also needs standalone ability definitions for icons and
tooltips. The mod therefore registers the production, passive-repair and AA
clones in the entity collection in addition to embedding them in the unit.
New fabrication and AA research definitions are added after native registration.

The runtime then audits the **actual registered objects**. It verifies their
identity and contents, rather than assuming that preparing a clone means the
native registry adopted it.

**Implementation:** `CloneAsset`, `Change`, `Rebuild`, `AddResearch`, `AddAbility`,
`AuditRegisteredTech` and `AuditProduction` in [Runtime.cs](../example/src/Runtime.cs).

### I.4 Roster, production and research

**PROVEN — runtime.** The mod removes production abilities by their produced
unit target, rather than hiding a named button and assuming the unit is gone.
It updates the associated HUD references and preserves other producer abilities.

For Khaaneph, it clones the original Assault production ability under the existing
`Ability_Produce_K_HonorGuard` key. Its target becomes `K_HonorGuard_MP`, its
research gate becomes `Tier_3_K_AssaultCruiser`, and its visible presentation
comes from Assault Cruiser production.

The resulting engineering chain is:

```text
Tier_1_G_Sandskimmers
  -> Tier_1_G_Catamaran             [visible Assault Ship fabrication]
  -> Tier_3_K_AssaultCruiser       [new Khaaneph-specific definition]
```

There are two separate requirements: the research item's dependency list and
its placement in the faction's branch/tier structure. The native research helper
checks both. Merely setting a prerequisite string did not make the new item
available through every relevant lookup.

| Definition | Current value or change |
|---|---|
| `Tier_3_K_AssaultCruiser` | Clone of Assault fabrication; 600 CU, 350 RU, 80 seconds; depends on `Tier_1_G_Catamaran`. |
| `Research_Buff_K_AssaultCruiser_AntiAir` | Clone of original Assault AA; 500 CU, 340 RU, 65 seconds; depends on the new fabrication. |
| `Tier_3_G_HonorCruiser` | Removed from the Khaaneph research tree. |
| `Research_Buff_G_HonorCruiser_Defenses` | Replaced in the Khaaneph upgrade branch by the new AA item. |
| Coalition/Soban Assault research | Dedicated fabrication and AA items removed; their other units and shared upgrades retained. |

The old Khaaneph Honor research points to shared base-game assets. Editing those
assets globally could change Gaalsien behavior. The working implementation clones
the relevant definitions and modifies the Khaaneph tree specifically.

Research applicability must be traced through its selectors. The visual presence
of Khaaneph armor does not make the cruiser eligible for every Khaaneph armor
upgrade. The current mod retains donor class and weapon behavior; it does not
broaden unrelated upgrade selectors. Some apparently relevant research assets
also exist in archives without appearing in the current multiplayer tree.

**Implementation:** `DataPlan.PatchTechTree`, `RemoveResearch` and producer audits
in [Runtime.cs](../example/src/Runtime.cs). Original costs, selectors and branches are
recorded in [the resource findings](../example/evidence/resources/RESOURCE_FINDINGS.md).

### I.5 Health, repair and anti-air

**PROVEN — runtime.** Health was derived from the original artillery comparison:

```text
Gaalsien Artillery Cruiser HP:       2500
Khaaneph Artillery Cruiser HP:       3350
Multiplier:                         3350 / 2500 = 1.34
Increase:                           34 percent
Original Assault Cruiser HP:        2700
Calculated result:                  2700 * 1.34 = 3618
Requested upward rounding to 50:     3650
```

The mod writes **3650** into the cloned unit attributes. Added armor geometry
does not itself alter health, armor statistics or navigation dimensions.

The original active `Ability_G_BattleCruiserActiveRegen` is removed. The mod clones
the actual Khaaneph Honor Guard passive, `Ability_G_HonorCruiserRegen`, as
`Ability_K_AssaultCruiserPassiveRegen`. Its existing status effect restores
**48 HP each second after 10 seconds without damage**. New damage interrupts the
repair condition. Native simulation behavior is reused; there is no per-frame
Unity script implementing a second health system.

The AA unlock is a **passive weapon enable**, not a user-operated toggle. The
retargeted `Ability_K_AssaultCruiser_EnableAir_MP` depends on the new AA research.
The native status effect enables weapon binding `AA_RIGHT`.

The test inspected a produced cruiser before and after research. It confirmed
that the same unit's AA passive activated and its air weapon became enabled.
It did not prove an air-target engagement or damage balance.

Repair was checked through actual simulation health: no healing after nine
seconds, then 2000 HP becoming 2144 after thirteen seconds, consistent with three
48 HP ticks after the delay. A second damage event restarted the delay and the
same repair rate resumed.

### I.6 Localization and voice routing

**PROVEN — runtime.** The tooltip formatter recognizes localization references
matching `ID_[A-Z_0-9]+`. The early `DOK_TRANSFER_...` names did not match and
appeared as untranslated text. The current keys start with `ID_DOK_TRANSFER_`.

`Runtime.GetLocalization` resolves only those additional keys and falls through
to the native manager for unrelated strings. The test opened the real production
tooltip and inspected its displayed `UILabel` text.

Audio requires more than changing the displayed unit name. The unit, production
ability, fabrication research and upgrade can each supply different dialogue
codes. The final implementation has two stages:

1. Retain the original Assault speech identity, `cas`, and AA identity, `aca`.
   Load the corresponding Coalition event hierarchy and route relevant Khaaneph
   events through it, without mutating the original queued event.
2. At `TryLoadClip`, substitute approved recordings from the loaded Khaaneph bank
   for supported Assault clip paths.

This preserves native event selection while changing the actual recording.
An Assault-looking path in a log does not necessarily mean a Coalition recording
was played: inspect the returned `AudioClip.name`.

| Response family | Final recording treatment |
|---|---|
| Selection and guard | Approved generic Khaaneph cruiser responses. |
| Movement and attack-move | Approved Khaaneph movement responses. |
| Attack | Approved Khaaneph attack responses. |
| Hold and stop | Approved Khaaneph stop responses. |
| Production completion | Generic Khaaneph readiness response. |
| Fabrication completion | Generic Khaaneph research/production-unlocked response. |
| AA completion | Generic Khaaneph research-complete response. |
| Rare combat-status and ability dialogue | Original Assault responses remain. |

Nineteen recordings are approved. They are existing game recordings, not generated
voices. Local speech recognition assisted inspection; it is not authoritative
transcription or a human listening test. No audio was uploaded for cloud voice
processing.

The completed live run observed actual Khaaneph `AudioClip` returns for selection,
natural production/fabrication events and AA completion. Both match cycles
produced the expected AA substitution. Other supported command mappings are
implemented and statically checked; the driver did not trigger every bark.

**Implementation:** [NativeVoices.cs](../example/src/NativeVoices.cs), `PrepareVoiceEvent`,
`BeforeSpeechBankLoad` and `GetAssaultVoiceClip` in [Runtime.cs](../example/src/Runtime.cs).

### I.7 Model authoring and integration

**PROVEN — runtime and export checks.** The model combines five skinned parts:

| Part | Origin and treatment |
|---|---|
| Weapons and aft suspension | Original Assault Cruiser; obsolete bridge-base geometry removed. |
| Main hull and angular bridge | Khaaneph Siege Cruiser geometry. |
| Port jaw/stabilizer | Khaaneph Production Cruiser geometry, bound to the front suspension. |
| Starboard jaw/stabilizer | Matching Production Cruiser geometry and binding. |
| Marked deck insert | Thin fitted cover over the former Siege launcher opening. |

The Baserunner influenced the visual language, but its decorative service pod and
mounting bracket were removed. Two actual recesses were cut around the missile
racks. Both cylindrical turret caps use the original pale material, with their
team-paint masks cleared at runtime.

The pipeline has three distinct stages:

1. **Extract for authoring.** UnityPy reads native meshes, UVs, material textures,
   skin weights, bind poses and transform hierarchies from the installed archives.
   The extraction leaves those archives unchanged.
2. **Build in Blender.** The kitbash preserves the original Assault transform
   names and relevant weapon bindings. Blender, GLB and FBX outputs are generated
   with packed or embedded textures and verified by round-trip import.
3. **Export for the game.** A project-specific exporter writes native-space mesh
   buffers to `model.kac` and copies PNG textures. The DLL reads those buffers
   directly through Unity's mesh APIs.

The game is **not** loading the GLB or FBX directly. Those are authoring/interchange
files. The installed runtime content is under `BepInEx/assets/KhaanephCruiser`.

`ModelAssets.CreatePrefab` clones the original unit prefab. It keeps all **57
native transforms**, the Animator/controller, physics, colliders and effect
attachment points. It removes the original three skinned renderer components,
then creates five renderer parts at each of three LODs: **15 renderers total**.
Native LOD thresholds are retained. The new forward armor follows the original
front suspension bones.

The source view asset and `UnitViewAttributes` are cloned independently before
their `ModelPrefab` is changed. The original donor view remains available for
campaign restoration.

Two integration details were decisive:

- **Canonical bind poses.** The exporter uses native rest transforms. A runtime
  pose borrowed from an animated preview is not a reliable rest pose.
- **Persistent shaders.** Native DLC unload destroyed the DLC shader objects
  referenced by cloned Khaaneph materials. The surviving materials then used
  `Hidden/InternalErrorShader`, causing the magenta hull. All custom materials
  now use the persistent base-game copy of the compatible `UNIT` shader.

Animation verification used both direct native clip sampling and controller
evaluation across real game frames after unit initialization. A freshly created
preview clone did not provide a valid immediate `Play`/`Update` test. The live
controller test confirmed missile-door motion, cannon recoil and stabilizer
steering; it was not a complete combat or destruction test.

**Implementation:** [ModelAssets.cs](../example/src/ModelAssets.cs),
[export-runtime-model.py](../example/tools/export-runtime-model.py),
[build-cruiser-kitbash.py](../example/tools/build-cruiser-kitbash.py) and
[kitbash_mounts.py](../example/tools/kitbash_mounts.py).

### I.8 Verification, installation and known limits

**PROVEN — recorded verification.** The final native run was on 13 October 2026,
from 18:17:44 to 18:23:08 UTC, or **21:17:44–21:23:08 Moscow time**. The temporary
driver completed two Khaaneph match cycles, a later match without Khaaneph and
three returns to the native preview. One match included all four factions.

The test combined independent forms of evidence:

| Check type | What it establishes |
|---|---|
| Original-file hashes | The investigated originals remain unchanged; the installer accepts only the supported files. |
| Hook verification | Calls target expected signatures and the old runtime ABI, including every registration exit. |
| Data tests | Clone isolation, research membership/next-tier rules, localization and speech boundaries. |
| Native simulation | Research, production, ownership, HP, AA enable and repair timing. |
| Native presentation | Real tooltip text, model instantiation, camera captures and selected playback callbacks. |
| Asset round trips | Blender/GLB/FBX geometry, names, texture availability and bounds remain consistent. |
| Reload checks | Current objects and valid shaders remain in use after preview/match transitions. |

The driver used extra resources, allied commanders, disabled replay recording and
4× simulation speed. These were temporary test settings. Its two DLLs were
removed afterward and are excluded from the release package.

The portable package includes the loader, two release DLLs, runtime geometry,
textures, hash manifest, installer, uninstaller and instructions. Installation
verifies payload hashes and supported game files before copying. Uninstall
checks ownership and hashes before removing only installed files.

The current release still has explicit limits:

- No real multiplayer peer test or mod compatibility handshake.
- No complete campaign mission regression test; campaign registration restoration was tested.
- No complete air-target combat, long-session stress or exhaustive animation/effect test.
- No custom wreck; the original Assault carcass and destruction definitions remain.
- No generic mod folder format, editor, arbitrary rig importer or independent-faction implementation.
- No confirmation yet from the second PC for the portable package in this evidence set.

## Part II — Hypotheses: extending the game

Everything in this part is a **HYPOTHESIS** or proposed development approach.
References to inspected native systems explain why a proposal is credible;
they do not establish that the proposal has been implemented.

### II.1 A general mod loader and content format

The most useful next abstraction would be a single shared runtime that owns
registration, object lifetime and diagnostics. Individual content mods would
declare their changes instead of each installing unrelated patches at the same
native sites.

A proposed separation of responsibilities is:

| Layer | Proposed responsibility |
|---|---|
| Game adapter | Version-specific hooks, native asset lookup, registry and preview integration. |
| Mod loader | Discover enabled mods, resolve dependencies and define a stable application order. |
| Content definitions | Declare units, faction loadouts, research, abilities, localization and asset mappings. |
| Asset toolchain | Convert authored models/audio/effects into formats supported by the adapter. |
| Validator | Check identities, references, asset contracts, conflicts and unsupported features. |
| Authoring interface | Present usable editing controls, previews, errors and packaging actions to humans. |
| Optional code extensions | Add behavior beyond the content schema through a documented programming interface. |

The current project provides useful implementations for parts of the game adapter
and asset toolchain. It has no general content schema or public extension API.

For illustration, a **future, unimplemented** folder layout could be:

```text
Mods/
  ExampleFaction/
    mod.json
    factions/
    units/
    research/
    localization/
    models/
    textures/
    audio/
    effects/
```

Similarly, the following is **design notation, not a supported input file**:

```json
{
  "schemaVersion": 1,
  "id": "example.desert-fleet",
  "version": "0.1.0",
  "gameBuild": "12339551",
  "scope": ["skirmish", "multiplayer"],
  "units": [
    {
      "id": "example.desert-fleet.assault-cruiser",
      "template": "G_Battlecruiser_MP",
      "maxHealth": 3650,
      "model": "models/assault-cruiser.asset"
    }
  ]
}
```

The `.asset` name above is a placeholder for a future supported model reference;
it is not an instruction to rename an FBX or a Unity file and expect it to load.

An SDK would need stable namespaced identities and explicit rules for overriding
existing content. Native entity names are case-insensitive in the inspected
collection, and duplicate additions replace existing entries. A validator should
report a conflict rather than silently relying on whichever mod happens to run
last. Dependencies and intentional overrides should be distinguishable.

**First proof:** load one small declarative HP or research change through the
proposed loader, disable it, and demonstrate original restoration across the
same preview/match/campaign transitions as the working mod.

### II.2 Adding independent factions

There are several different goals that people call “adding a faction”:

1. Change the roster or appearance of an existing faction.
2. Add a distinct selectable faction that inherits an existing base family.
3. Add a faction with independent identity, loadout, research, AI and presentation.

Only the first is demonstrated by the current mod. The latter two are credible
research targets, but the third is substantially broader.

The native lobby is not simply a four-entry unit list. It collects base commander
options from `LevelManager.CommanderAttributes` and adds eligible faction DLC
descriptors. `SpawnAssigner.GeneratePlayerSelections` then resolves the selected
commander either through a DLC header or the base commander array.

That provides an extension point, but it also reveals coupled assumptions:

- `CustomizationSettings` initializes `UnitSkinPackID` with **two entries**.
- Several paths index customization by the base-family selection value.
- Fleet preview selection uses existing model-set arrays.
- UI selection, commander descriptions and actual loadouts must resolve the same identity.
- DLC-faction AI options depend on available AI archetype data.

This does **not** prove an immutable two-faction engine limit. It shows why
appending a unit roster or drawing a fifth button is insufficient.

A proposed implementation would introduce a mod-owned faction registry, then
adapt the selection and loadout boundaries to use it. That registry would need
to carry at least:

| Faction concern | Required information or integration |
|---|---|
| Identity | Unique stable mod/faction ID and localized display name. |
| Gameplay | Commander definition, starting units/resources, tech tree, abilities and production roster. |
| Selection | Lobby options, random selection and persistence in user settings. |
| Preview | Model arrangement, camera placement, colors, emblem and optional faction presentation. |
| AI | Compatible archetypes, build/research choices and unit-role treatment. |
| Audio/UI | Voice routing, notifications, icons and any genuinely distinct interface requirements. |
| Loading | All definitions and assets loaded before their consumers initialize. |
| Persistence/networking | Stable representation in match setup, replays, saves and peer compatibility checks. |

A mod-defined faction should have its own content-loading route. Treating an
invented platform DLC identifier as a registered faction would not establish that
the native ownership, descriptor and loading paths understand it. Original DLC
dependencies should continue to use the game's legitimate ownership checks.

**First proof:** use existing base-game assets to create a fifth selectable test
faction. Initially reuse a compatible commander/AI template so the experiment
isolates faction identity and loading rather than art production. Demonstrate
its unique tech tree, human and AI selection, correct starting units, preview,
two consecutive matches and return-to-menu behavior. Then test against a second
PC before claiming multiplayer faction support.

### II.3 Adding units and mechanics

The inspected registry accepts named entity definitions. This supports a plausible
path for adding a unit under a new key, but our current cruiser retains an
existing key and therefore is not the required proof.

A proposed new-unit workflow is:

1. Clone a suitable complete unit container and give it a new identity.
2. Clone mutable attributes that will differ from the template.
3. Preserve or remap weapon, movement, detection, storage, HUD and view connections.
4. Create its production ability and research requirements.
5. Add that ability to the appropriate producers and their command presentation.
6. Register the unit and all required standalone abilities/research at the correct boundary.
7. Update applicable research selectors and AI knowledge deliberately.
8. Verify production, ownership, targeting, repair, death, save/reload and faction isolation.

Registration should happen before commander-specific buffed definitions are
created. The native collection flushes its user-specific type cache when a new
base entity is added afterward. Arbitrary additions during an active simulation
would need a separate design and synchronization proof.

“Removing a unit” should normally mean removing its availability from a roster,
producer or starting loadout while preserving definitions still referenced by
other content. Deleting its global definition is a different operation: research,
abilities, saves, scenarios or another faction may still reference it.

Replacing or hiding the mesh is also independent of removing a gameplay unit.
An invisible unit can still exist, consume population, collide and fire.

**Mechanics based on existing primitives** are the most promising: different
weapons, status effects, costs, repair rates, resource handling or combinations
of native ability behavior. **Entirely new behavior** may require simulation
processor or command hooks, additional state and save/network integration.
It should not be implemented casually in a Unity render-frame callback.

**First proof:** add one new unit ID based on an unchanged native template,
produce it beside the original, and show that changing its HP affects only the
new unit. Add more complex abilities only after that isolation test passes.

### II.4 New models, animations and wrecks

The demonstrated path is strongest for new geometry fitted to a compatible
existing rig. A broader model system would remove the current assumptions of
57 transform names, five parts and three LODs, while retaining validation for
the actual target unit's requirements.

Two possible content routes deserve separate evaluation:

- **Extend the custom runtime format.** Generalize mesh, material, skeleton and
  attachment descriptions and provide a Blender exporter. This builds directly
  on the working geometry importer.
- **Load compatible Unity AssetBundles.** Bundles can carry models, textures,
  audio and scenes, according to the [Unity 5.2 AssetBundle manual](https://docs.unity3d.com/520/Documentation/Manual/AssetBundlesIntro.html).
  This could be useful for prefabs and particle systems, but a newly authored
  third-party bundle has not been tested with this mod.

For the bundle route, matching the game's Unity 5.2.2f1 Windows environment is a
conservative first compatibility target, not a proven guarantee. Arbitrary
bundles from modern Unity versions should not be assumed compatible. The older
`CreateFromFile` API also has format constraints; the archived
[Unity 5.2 API reference](https://docs.unity3d.com/520/Documentation/ScriptReference/AssetBundle.CreateFromFile.html)
describes it as accepting uncompressed bundles.

A truly new rig requires more than a mesh import. The model must agree with
turret yaw/pitch definitions, muzzle transforms, physics wheels, docking points,
animation parameters and effect references. Animation clips and controllers
would need an explicit import/retargeting path or deliberate reuse of native
ones. An FBX that animates correctly in Blender does not establish that the game
will bind its controller correctly.

Wrecks should be treated as their own content. The current live mesh replacement
leaves the original carcass in place. A complete new unit should deliberately
define its death sequence, carcass, collision and any salvage behavior instead
of assuming that the live model automatically supplies them.

**First proofs:** import a second model on another native rig; then test a small
custom animated attachment; then replace a carcass. These establish different
capabilities and should be reported separately.

### II.5 External audio and new dialogue

The existing clip-return hook is a useful boundary for importing new recordings,
but the final mod only returns clips from an already loaded native bank.

A proposed external-audio loader could decode a supported file into PCM data,
create a Unity `AudioClip`, and return it through a controlled alias map. A first
implementation could limit input to a documented WAV format, then add conversion
tools for other formats. Actual decoder/API compatibility and resource lifetime
must be tested on the old runtime.

There are two distinct audio tasks:

| Task | Likely integration |
|---|---|
| Replace a recording for an existing event | Reuse the demonstrated event-to-clip lookup, with an externally loaded clip. |
| Add a new event or an entirely new unit voice family | Extend event translation/selection or implement a mod-owned mapping that preserves relevant unit/action context. |

The second task is harder because native Fabric dialogue hierarchies choose
responses based on more than a file name. A useful SDK would expose concepts
such as selection, move, attack, production complete and upgrade complete, with
optional variations, cooldowns and priorities.

Weapon sounds and looping engine/effect sounds may follow different paths from
unit dialogue. The VO hook should not be advertised as a universal audio API.
Looping, attenuation, interruption and simultaneous playback need their own tests.

**First proof:** replace one existing selection response with a known external
WAV, confirm the actual clip returned to playback, listen to it, then repeat
after a full match/menu/bank reload. Next test a looping engine or weapon effect
through its own native audio path.

### II.6 Effects and projectiles

Inspected weapon view data includes effect definitions, emission strategy and
tracer/impact probabilities. `WeaponEffect` carries an effect prefab, sound and
emission-bone association. The unit view contains machinery for attaching
effects to configured muzzle or center-emission transforms.

This suggests a staged approach:

1. Remap a weapon to an existing native effect.
2. Clone that effect and change exposed visual properties.
3. Import a simple custom effect prefab or construct one through supported APIs.
4. Connect it to native firing, impact, damage or death events.
5. Validate pooling, cleanup, visibility, LOD behavior and repeated use.

Gameplay projectiles and projectile visuals must be considered separately. A new
tracer appearance need not change the damage calculation. A new gameplay
projectile, targeting style or area-of-effect mechanic needs corresponding
simulation definitions and deterministic behavior.

Likewise, disabling a muzzle flash should not disable the weapon. The SDK would
need an explicit distinction between visual/audio overrides and gameplay rules.

**First proof:** replace one weapon's muzzle effect while leaving its damage and
fire timing unchanged. Observe the actual spawn and confirm that no pooled
objects, sound loops or effects survive incorrectly after unit death or unloading.

### II.7 Multiplayer, saves and compatibility

The inspected simulation uses fixed-point types and returns a checksum from its
tick. This makes deterministic content and behavior an important design concern.
It does not establish exactly which mod assets the current native protocol
compares, or that identical files alone guarantee synchronization.

A proposed compatibility system should record:

- The supported game adapter/build and loader version.
- Enabled mod identities, versions and dependency order.
- A canonical digest of gameplay definitions and required content.
- The schema/version used to interpret those definitions.

Peers would compare that information before loading a match. The digest should
come from canonical content and a stable ordering, not local absolute file paths
or unspecified dictionary enumeration. Whether some cosmetic differences can
be permitted is an **OPEN QUESTION**, not an established exemption.

Saves and replays also need stable content identity. Renaming a unit or removing
a mod can invalidate referenced definitions. A future loader should record the
required mod profile and report unavailable dependencies instead of loading
different content under the same name.

Code extensions need stricter treatment than ordinary asset replacements. Any
extension influencing simulation state must use the simulation's timing, state,
numeric and random-number conventions. Local wall-clock time and render-frame
timing are poor foundations for synchronized gameplay.

**First proof:** run matching builds on two PCs, play a sufficiently long match
with the changed unit and research, and inspect synchronization diagnostics.
Then intentionally introduce a mismatched definition and verify that the
proposed loader rejects it before the match starts.

### II.8 A sensible sequence of proofs

These are research milestones, not an implementation schedule or completion
claim. Each milestone resolves a specific uncertainty.

| Sequence | Experiment | Evidence required before promoting the capability |
|---|---|---|
| 1 | Additional selectable faction using existing assets | Unique selection/loadout/tree; human and AI play; repeatable preview/match reload. |
| 2 | New unit ID beside its donor | Independent data, production, HUD, research, ownership and lifecycle behavior. |
| 3 | External audio clip | Known recording reaches playback, is audible and survives unload/reload. |
| 4 | Custom effect | Native event triggers it; attachment, pooling and cleanup remain correct. |
| 5 | Generalized model import | A second rig/content example works without cruiser-specific assumptions. |
| 6 | Declarative content loader | At least two independent example mods can be enabled/disabled and validated consistently. |
| 7 | Network and persistence integration | Matching peers work; mismatches fail clearly; profile-aware save/replay behavior is demonstrated. |
| 8 | Human-facing editor and SDK release | Authoring tasks succeed using documentation and tools without editing internal engine fields by hand. |

The order can change when an experiment is independent. The important boundary
is between proving a feature and building an editor that assumes it already works.

### III.2 Registry, containers and identity

**PROVEN — source/data, with the transfer verified at runtime.** A useful model
of registration is:

```text
EntityRegistryAsset + additional current faction assets
  -> ShipbreakersMain.InitializeEntityManager
  -> flatten AssetContainer / AssetBase / MultiAssetBase data
  -> EntityTypeAttributes named by the source asset
  -> EntityTypeCollection
  -> simulation and presentation lookups
```

`ResetEntityManager` gathers required entity containers from currently loaded
faction DLC packs and adds the faction's referenced tech asset before rebuilding
the collection. It does not simply keep the first registry from startup forever.

An `AssetContainer` is a Unity `ScriptableObject` that exposes its contained data
through enumeration. `UnitAssetContainer` specializes that container for unit
definitions:

| Container field | Responsibility |
|---|---|
| `m_Attributes` | Core unit attributes and initialized weapon/loadout relationships. |
| `m_Movement` | Movement attributes. |
| `m_Detectable` | Detection-related data. |
| `m_View` | Model and presentation bindings. |
| `m_HUD` | Unit and command-panel presentation. |
| `m_Audio` | Audio hook-up data. |
| `m_Death`, `m_QuadrantDamage` | Death/carcass and damage presentation. |
| `m_Weapons`, `m_Abilities` | Weapon and ability assets included with the unit. |
| Storage, harvester, hangar and other optional fields | Specialized capabilities appropriate to the template. |
| Inherited `mDataCache` | Prepared flattened data consumed by enumeration. |

The container's `OnEnable` prepares cached data and initializes unit/storage
attributes. The working patch explicitly rebuilds this state after changing
references.

Native entity lookup is case-insensitive. `EntityTypeCollection.Add` replaces a
duplicate name and logs a warning. It also clears commander-specific type caches
if additions happen after those caches exist. These behaviors are reasons to
establish identities and registration order early, especially for multiple mods.

Keep these forms of identity separate:

1. **Unity asset name:** often used as the registered entity key.
2. **Managed named-data identity:** initialized through `NamedObjectBase.InitializeName`.
3. **Visible localized title:** a UI string or localization key.
4. **Unit class, weapon binding and research selectors:** gameplay classification and targeting.

Changing one does not automatically update the others. The current mod
deliberately keeps the Khaaneph entity key, initializes new research names and
uses different visible Assault titles.

**Source:** [AssetContainer.cs](Native-API-Index.md#assetcontainer),
[UnitAssetContainer.cs](Native-API-Index.md#unitassetcontainer),
[EntityTypeCollection.cs](Native-API-Index.md#entitytypecollection) and
`InitializeEntityManager`/`ResetEntityManager` in
[ShipbreakersMain.cs](Native-API-Index.md#shipbreakersmain).

### III.3 Loading and object lifetimes

**PROVEN — runtime.** Preview content and match content can contain different
Unity object instances with the same names. The preview has its own content/DLC
management path. Unloading a bundle can destroy objects that an ordinary C#
reference still appears to hold.

The implemented registration sequence is:

1. Restore saved fields on original Unity assets that are still alive.
2. Clear the current asset index and per-registration HUD/tech caches.
3. Index the registry, additional entities and current loaded faction packs.
4. Determine the game mode.
5. For supported skirmish/multiplayer registration, prepare and apply the transfer.
6. Patch producers and research trees; let native registration run.
7. Add supplemental research/ability definitions and audit the resulting collection.

Preview preparation separately indexes the exact faction pack passed to the
preview hook. The transfer cache is reused only when the source and destination
unit references match the current objects. A later match without Khaaneph clears
the transfer's current Khaaneph references.

Three different cache/lifetime problems occurred:

| Failure | Explanation | Working correction |
|---|---|---|
| Research missing after match start | The mod had prepared obsolete preview objects rather than the newly loaded match assets. | Re-index current registry/packs before each registration and audit the registered tree. |
| Magenta hull after unloading | Cloned materials survived while their DLC shader objects were destroyed. | Bind custom materials to the compatible persistent base-game shader. |
| Old voice cache after bank reload | The native clip dictionary object can be reused while its clip objects are replaced/unloaded. | Refresh cached Khaaneph clip references when the selected Unity clip is missing or destroyed. |

Unity's overloaded null behavior matters. A destroyed Unity object can compare
equal to null even though a managed reference exists. Reference equality is useful
for distinguishing current asset instances, but it is not an independent test
that the native object is still alive.

The runtime's diagnostic path comes from its loaded assembly location. The tested
Unity child AppDomain had no useful `ApplicationBase`; an early logger threw while
trying to use it. The working logger contains its own failures so diagnostics do
not become a reason for game initialization to fail.

The repeated-load tests establish these specific fixes. They do not establish a
general memory bound or unlimited-session leak freedom. A reusable SDK should
explicitly own allocation, restoration, cache eviction and disposal rather than
assuming that retained references solve every lifetime problem.

### III.4 Research, abilities and buffs

**PROVEN — source/data and targeted runtime tests.** Research availability is a
combination of several conditions. The inspected `ResearchHelperShared` checks
active research, completion, tree membership, next-tier validity, dependencies,
resources and locks.

The principal data relationships are:

```text
Faction definition
  -> tech-tree asset
     -> engineering branches and tiers
     -> upgrade entries
        -> named research item
           -> dependency names, cost, time and completion behavior

Producer unit
  -> production ability
     -> research requirements
     -> produced unit key
```

This explains why a research item can exist in the registry yet fail to appear
or be available in a faction's engineering panel. It can be absent from the
appropriate tree or not belong to a valid next tier. Similarly, enabling a
production ability without making its required research attainable creates a
unit that the player cannot normally build.

Abilities have another split: unit-embedded attributes drive unit behavior, while
standalone registered ability data also serves native UI/validation lookups.
The current mod keeps those references consistent.

`RequiredResearchIsLocked` means permanently unavailable through the commander's
locked-research configuration; it does not mean “not completed yet.” The final
AA test instead checks completion state, passive activation and the actual air
weapon's enabled flag.

Buff applicability must be inspected through selectors such as `UnitType`,
`UseAsPrefix`, `UnitClass` and its flag operator. A title containing “armor” or
“cruiser” is not enough. The original Khaaneph ship-armor upgrades in the focused
evidence target particular ship names and do not automatically include cruisers.
Unused archive research is also not necessarily reachable multiplayer research.

For health behavior, native processing distinguishes damage and healing. The
observed health-over-time processor advances timers in 125 ms increments and
applies its configured tick duration. Reusing the native ability/status-effect
path preserves that timing better than an independent render-frame repair loop.

### III.5 Faction selection and commander loadouts

**PROVEN — source/data.** Do not collapse the following identities into one number:

| Identity | Observed role |
|---|---|
| `CustomizationFactionSetting` / `CommanderDescription.FactionIndex` | Base-family selection used in customization and base commander lookup. |
| `FactionAttributes.ID` | Gameplay faction identity; the inspected Khaaneph faction asset has ID 4. |
| `DLCPackID` / `SelectedUnitSkinPack` | Selection of a registered native pack that may supply a variant commander/loadout. |
| Entity/tech-tree names | Keys connecting actual units, production, research and registered data. |

The two-entry customization array is therefore not evidence that Khaaneph's
gameplay identity is simply faction index 1 or that the game supports only two
distinct gameplay factions. It is evidence of a base-family assumption in one
part of the system.

`GameLobbyView.GetFactionOptions` iterates the base commander array, then eligible
faction DLC descriptors, and adds random selection. For DLC AI choices, it checks
for suitable AI archetype assets. `SpawnAssigner.GeneratePlayerSelections` tries
the selected faction pack's commander first, otherwise indexing the base commander
array with `FactionIndex`.

`CommanderAttributesData` carries starting units/resources, starting and locked
tech, population settings, faction data, buffs and AI archetypes. Consequently,
a new faction needs a complete loadout definition, not just a new `FactionName`.

Preview presentation has separate model-set arrays and temporary customization
controllers. Extending a lobby option alone will not create a matching fleet
display. Customization saving and random faction selection must also support the
new identity consistently.

The current patch leaves native entitlement and ownership checks intact. The
proposed additional-faction registry in Part II would be new work; it is not an
existing unadvertised feature of the release.

### III.6 Simulation and presentation

**PROVEN — source/data.** The architecture separates gameplay simulation from
Unity presentation. `BBI.Game` contains simulation code and fixed-point values;
`BBI.Unity.Game` presents unit state through models, UI, effects and audio.

| Simulation concern | Presentation concern |
|---|---|
| Unit HP, ownership, weapon rules and research completion | Model, colors, tooltip and selection display. |
| Movement dimensions and gameplay state | Visible suspension, turret pose and effects. |
| Commands and ability/status-effect processing | Animation parameters, audio events and particle spawning. |
| Tick state/checksum | Unity frame updates and camera rendering. |

Some data bridges both sides. Turret definitions, for example, connect simulation
weapon bindings to visible bone rotation and muzzle effects. A mod author must
trace those links rather than treating the model as the source of weapon rules.

The inspected simulation tick accumulates a checksum, and native random helpers
use the simulation's configured random-number generator. These are concrete
reasons to preserve deterministic behavior in gameplay extensions. The exact
network compatibility policy remains an open research area.

Registration also initializes an entity system with explicit values of 5000 and
48 in this build. Those literals are **not** a demonstrated public unit-capacity
setting or permission to assign arbitrary component IDs. Expanding simulation
components or capacities would need to trace their other consumers and masks.

The temporary test driver respects this division: scene/UI operations run through
a main-thread hook, while simulation assertions and native commands run at a
simulation tick boundary. It does not prove that arbitrary cross-thread access
to Unity or simulation objects is safe.

**Sources:** [Sim.cs](Native-API-Index.md#sim),
[ShipbreakersMain.cs](Native-API-Index.md#shipbreakersmain),
[UnitView.cs](Native-API-Index.md#unitview) and
[LiveProbe.cs](../example/tests/LiveProbe.cs).

### III.7 Model, rig and material contracts

**PROVEN — source/data and the current model integration.** Before editing a
model, inspect the complete prefab hierarchy and its view definition. Mesh bones
are only part of that contract.

| Contract | Why it matters |
|---|---|
| Transform names and parent relationships | Animation paths and named attachment lookups depend on them. |
| Rest bind poses and vertex weights | They determine how geometry follows the skeleton. |
| Turret yaw/pitch and simulated origins | They connect visible weapon orientation to native unit/weapon behavior. |
| Muzzle/center emission transforms | Native firing effects attach through these names. |
| Wheels, suspension, colliders and rigid body | They affect presentation physics and moving assemblies. |
| Camera target and selection/visibility behavior | They influence focus and how the unit is presented. |
| Animation controller and parameters | Native code drives named booleans/floats/triggers. |
| Materials, textures and team masks | They connect authored surfaces to native lighting, team paint and visibility. |
| Carcass/death references | They determine what remains after the live model is replaced or destroyed. |

The current rig retains names including:

```text
RIG_BattleCruiser_Chassis
RIG_BattleCruiser_FrontTurret_Rot
RIG_BattleCruiser_FrontTurret_Pitch
RIG_BattleCruiser_FrontTurret_Barrel_L
FX_FrontTurret_Muzzle_L
RIG_BattleCruiser_MissileBay1_Hatch1
RIG_BattleCruiser_Susp_FLT
RIG_BattleCruiser_Susp_FRT
```

These are examples, not the complete list. The full 57-name sequence is recorded
in [model.json](../example/assets/runtime-model/model.json).

The original controller is `Unit_G_BattleCruiser_AnimationController`. Inspection
found six layers, including left/right missile pods, front/rear cannons and
turning. Relevant parameters include `MissilePodL`, `MissilePodR`, `FireFwd`,
`FireRear` and `SteeringVectorX`. The controller's native clips include missile
door states, cannon recoil and left/right/straight steering poses.

The Khaaneph Siege, Production and Baserunner donors also have inspected native
animation/controller data. Their geometry does not automatically bring their
controller behavior into the new unit. The kitbash deliberately uses the Assault
controller and binds the added front armor to its compatible suspension bones.

Coordinate conversion is an authoring concern, not a cosmetic adjustment. The
working scripts swap Unity's Y-up and Blender's Z-up axes using a matrix. That
axis swap changes handedness, so the pipeline also handles winding and tangent
signs. The runtime exporter converts back through the native root transform,
transforms normals correctly and exports rest bind matrices in the expected space.
Blindly rotating the final mesh can leave bone matrices, winding or hardpoints
inconsistent even if a static view looks correct.

Material properties used by the runtime include `_MainTex`, `_BumpMap`,
`_OcclusionMap`, `_OverlayMask` and `_Surface`. The native view/customization code
uses `_BaseColor` and `_TrimColor` for team colors. The runtime clones native
material templates, loads its own PNGs and binds the persistent compatible shader.
Plain frame material and white caps clear the overlay mask where appropriate.

The PNGs are not a universal modern PBR texture set. Preserve the donor's channel
meaning and property mapping. A future generalized importer should validate
normal packing, color space, masks and shader expectations explicitly rather
than assuming a Blender material is equivalent to the game's material.

For exports, the current pipeline normalizes at most four bone influences per
vertex and keeps each mesh within its 65,535-vertex limit. Vertex count may grow
when UV seams, normal splits and tangents require duplicated runtime vertices.
The largest LOD0 part in this export has 36,390 vertices; the total across parts
is not the relevant per-mesh bound.

[native material contracts](../example/evidence/models/native-material-contracts.json),
[UnitViewAttributes.cs](Native-API-Index.md#unitviewattributes) and
[UnitView.cs](Native-API-Index.md#unitview).

### III.8 The KAC2 model file

**PROVEN — current exporter/reader and runtime.** `model.kac` is a project-specific
binary format, not a native game archive format, AssetBundle, FBX or general
public interchange standard. `model.json` is a human-readable export summary;
the runtime reads the binary file for geometry.

Version 2 uses little-endian integers and 32-bit floating-point values. Strings
are an `int32` UTF-8 byte length followed by those bytes. They are not the default
.NET `BinaryWriter.Write(string)` representation.

| Order | Stored data |
|---|---|
| Header | Four ASCII bytes `KAC2`, then `int32` format version 2. |
| Bones | `int32` count, ordered bone-name strings, then one 4×4 bind matrix per bone. |
| Materials | Count and material records: name, native template name, plain/white-cap flags as integers, four color floats, texture-property records. |
| Texture-property record | Property-name string, relative PNG path, two scale floats and two offset floats. |
| Meshes | Count and records: part name, LOD integer, vertex count, vertex records and submeshes. |
| Submesh | Material index, index count and triangle indices as `int32` values. |

Each vertex is written with Python's `struct` format **`<16f4i`**:

```text
position xyz                3 floats
normal xyz                  3 floats
UV xy                       2 floats
tangent xyz + sign          4 floats
bone weights                4 floats
bone indices                4 integers
```

That is 80 bytes per vertex. Bind matrices are written row by row; the reader
assigns their individual matrix elements by row and column.

The three export passes use decimation ratios **1.0, 0.48 and 0.19**. They produce
five mesh records each, so the binary contains 15 records. The runtime keeps the
original LOD group's transition heights and gives each LOD its five renderers.
It creates bone arrays by matching exported names to the retained prefab transforms.

The loader validates format/count bounds, LOD range, material indices, texture
path containment and the end of the file. It also requires exactly 57 bones and
15 mesh records for this asset. Those exact checks are appropriate for the
current mod but would need redesign for a generic importer. They are not a
complete validator for arbitrary untrusted geometry.

Persistent meshes, materials, textures and template prefabs are held by the
runtime. Native prefab/controller/physics objects supply the wrapper, while the
new mesh buffers supply its appearance. No new Unity script type is embedded
inside the binary.

**Authoritative pair:** [export-runtime-model.py](../example/tools/export-runtime-model.py)
and [ModelAssets.cs](../example/src/ModelAssets.cs). Change them together when changing
the format; do not infer a different format from the `.kac` extension alone.

### III.9 Audio and localization

**PROVEN — source/data and selected playback tests.** Unit dialogue has two
separable layers: choosing a native event/response and resolving its audio clip.
The working mod exploits that separation rather than rebuilding the entire
dialogue system.

`VoiceOverEvent` includes action, faction, summary/detail and unit context.
`VOController` and the native dialogue hierarchy translate those into a selected
recording reference. `AudioAssetBundleLoader` resolves that reference against
`mClipDictionary` with an `assets/content/audio/bundled/` prefix.

Examples of relevant action/code conventions in this implementation:

| Token | Observed use |
|---|---|
| `sel`, `mov`, `atk`, `atm` | Selection, movement, attack and attack-move clip families. |
| `stp`, `hld`, `grd` | Stop, hold and guard clip families. |
| `rsh`, `upg`, `prc` | Research, upgrade and production-completion recording paths used by the mod. |
| `cas` | Original Assault speech identity. |
| `aca` | Original Assault anti-air upgrade identity. |
| `def` | The old Honor Guard defense research announcement that must not be reused for Assault AA. |

These are observed mappings, not a complete native vocabulary. In particular,
an ability event and its eventual production-completion recording need not use
the same action token.

The AA completion event puts its research VO code in `SecondarySummary`.
Inspecting only the unit's primary speech code missed this and allowed an Honor
Guard announcement to remain. The final event predicate handles that field for
the relevant fleet-operations research events.

Native unload releases clip data and clears the dictionary. A dictionary object's
identity can remain unchanged across that operation, so caching its reference is
not sufficient. The approved-clip selector also refreshes when an old Unity clip
has been destroyed. Its FNV-style hash selects a stable approved variation for
an original reference without consuming simulation randomness.

Localization has its own formatting stage. `ObjectFormatter` first decides
whether a token looks like an ID, then the localization manager resolves it.
Hooking `GetEntry` cannot fix a string that the formatter never treats as a
localization reference. The current new descriptions are English strings;
automatic multilingual authoring/localization is not part of this mod.

[VOController.cs](Native-API-Index.md#vocontroller),
[NotificationController.cs](Native-API-Index.md#notificationcontroller),
[AudioAssetBundleLoader.cs](Native-API-Index.md#audioassetbundleloader),
[ObjectFormatter.cs](Native-API-Index.md#objectformatter) and

### III.10 Working with code and authoring tools

The following commands describe the **existing source project**, not a finished
public SDK. Review scripts before running them. Several authoring scripts use
project-specific paths and overwrite generated outputs or the current Blender
scene/file. Keep an independent copy of hand-edited artwork.

#### Code workflow

The host build uses the Windows .NET Framework C# compiler, while the runtime
DLLs reference the game's installed `mscorlib`, `System` and Unity/BBI assemblies.
The build uses `/nostdlib+` and explicit references to produce old-Mono-compatible
metadata. The verifier checks a .NET 2 metadata target and `mscorlib` major version 2.

A modern SDK's default target framework is not interchangeable with that setup.
The practical first step is reproducing the existing build, then changing one
contained behavior. Source examples should remain compatible with the compiler
and available game APIs rather than assuming current .NET facilities.

From the source-project root:

```powershell
# Change the path if the game is installed elsewhere.
$gamePath = 'C:\Program Files (x86)\Steam\steamapps\common\Deserts of Kharak'

.\tools\build.ps1 -GamePath $gamePath
.\tools\verify.ps1 -GamePath $gamePath
```

`build.ps1` compiles the runtime and patcher. `verify.ps1` builds/runs hook and
data verifiers against the original assemblies and focused resource evidence.
It does not launch a match or replace native game files.

Important source roles are:

| File | Role |
|---|---|
| [src/Patcher.cs](../example/src/Patcher.cs) | Preloader contract, build guard and exact managed hook insertion. |
| [src/Runtime.cs](../example/src/Runtime.cs) | Registration lifecycle, cloning, roster/research/ability changes, localization and event routing. |
| [src/ModelAssets.cs](../example/src/ModelAssets.cs) | KAC2 reading, texture/material loading and skinned prefab construction. |
| [src/NativeVoices.cs](../example/src/NativeVoices.cs) | Approved Khaaneph clip mapping and native-bank cache handling. |
| [tests/VerifyHooks.cs](../example/tests/VerifyHooks.cs) | IL/ABI, initialization and supported-build checks. |
| [tests/VerifyData.cs](../example/tests/VerifyData.cs) | Data isolation, native research-rule and localization/voice-boundary checks. |
| [tests/LiveProbe.cs](../example/tests/LiveProbe.cs) | Temporary native game driver for preview, matches, UI, animation and audio assertions. |

Reflection helps reach private data, but it does not eliminate type distinctions.
The project's `Reflect.Get` reads fields, whereas `Reflect.Property` reads a
property. A similarly named interface property or compiler-generated backing
field can require a different lookup. One early voice integration failed because
it treated commander attributes as the wrong member kind.

For managed changes, useful implementation checks include:

- Verify the original file hash before applying version-specific hooks.
- Validate the exact owner, method signature and static/instance convention.
- Keep patcher dependencies from loading the target game assembly too early.
- Preserve branch/exception-handler control flow when inserting hooks.
- Confirm that every registration exit passes the required post-registration hook.
- Read the resulting registered data; do not infer success from logs saying a clone was prepared.

These are working practices from this implementation. A new hook needs its own
control-flow and ABI verification; copying an existing prefix is not sufficient.

```powershell
$blenderPath = 'C:\Program Files\Blender Foundation\Blender 5.1\blender.exe'
```

not a drop-in exporter for arbitrary Blender scenes.

moving parts. A visually convincing front render can hide floating attachments,
uncovered openings or clipping during motion. Source/export bounds and packed
textures are useful checks, but only a game render establishes the actual shader
and lighting result.

#### Native tests and release packaging

The current temporary driver can be built and installed with:

```powershell
# Close the game first. These install temporary development-only DLLs.
.\tools\build-live-probe.ps1 -GamePath $gamePath
.\tools\install-live-probe.ps1 -GamePath $gamePath
.\tools\launch.ps1 -GamePath $gamePath -Windowed
```

It is a purpose-built cruiser regression driver, not a generic test framework.

The probe patcher runs after the release patcher so it can observe substituted
audio returns as well as original lookup returns.

```powershell

  -PackagePath .\release\KhaanephAssaultCruiser
```

The source contains generated outputs and research dependencies that are not
included in the installation ZIP. Conversely, players need only the verified
installer package and the supported game/DLC; they do not need the authoring
environment.

### III.11 Troubleshooting

These observations came from this project. Use the stated diagnosis as a
starting hypothesis when the surrounding conditions differ.

| Symptom | What happened here | Useful next inspection |
|---|---|---|
| Empty or nonsensical setup menus shortly after launch | The same behavior occurred with the loader disabled while EOS/platform initialization was pending. | Compare with an unpatched baseline and wait for native initialization, rather than immediately changing faction data. |
| Preview works, but research disappears in a match | Stale preview asset references survived into a new match's registration. | Log instance identities and inspect the actual registered faction tree after registration. |
| Preview reverts after leaving a match | Preview content reloaded fresh faction assets. | Prepare the newly supplied preview pack, not only the first one loaded. |
| Correct prerequisite, missing research option | Native rules also check branch membership and valid next tiers. | Inspect `ResearchHelperShared` result and both tree and research definitions. |
| Build/ability data looks correct, but tooltip/icon lookup fails | Standalone ability definitions were missing or inconsistent with unit-embedded data. | Resolve the ability through the command panel's registry path. |
| AA “toggle” cannot activate | The donor upgrade enables a passive weapon; it is not a toggle. | Check completed research, passive state and `AA_RIGHT.Enabled`. |
| Repair rate does not match the named donor | Several similarly named or unused repair definitions exist. | Follow the actual ability reference from the unit container to its applied status effect. |
| Description displays a raw token | The formatter did not recognize a localization ID without the required prefix. | Check `ID_` token recognition, then the localization lookup. |
| Upgrade says “Honor Guard” | AA has a separate research VO code and event field. | Inspect `SecondarySummary`, `aca`/`def` routing and the actual returned clip. |
| Hull is magenta, engine remains textured | Khaaneph materials lost their DLC shader while base-game material references remained valid. | Log shader names/support after unload; compare with a persistent compatible shader. |
| Geometry is distorted when the unit animates | A potential bind-space, coordinate, weight or hierarchy mismatch. | Compare canonical rest matrices and bone names, then sample the original clips. |
| Animation test reports no motion | Immediate updates on an uninitialized preview clone did not reproduce the native lifecycle. | Compare with the unmodified donor, then evaluate an initialized controller over multiple game frames. |
| Errors appear on every return to the menu in the test | The driver started a second preview load while the native exit path was already loading it. | Wait for the native coroutine/camera instead of making a duplicate load request. |
| Logger itself aborts startup | The tested Unity child domain lacked the expected application base. | Use a reliable assembly-relative path and contain diagnostics failures. |

Inspect the game's own logs as well as the mod log. A healthy patch run can
coexist with unrelated online-service or native shader diagnostics; an exception
must be attributed by its call path and reproduction, not by proximity alone.
The inverse is also true: a pre-existing native warning is not grounds to ignore
a newly introduced rendering or loading regression.

Recommended test progression is: original baseline, one changed definition,
registered-data inspection, one native behavior, repeated unload/reload, then
the relevant combat, persistence and network scenarios. Change the smallest
independent variable that distinguishes competing explanations.

### III.13 Glossary

| Term | Meaning in this document |
|---|---|
| ABI | The binary calling contract: assembly identity, method names, argument/return types and calling conventions. |
| Asset | A stored or loaded piece of content/data, such as a mesh, texture or unit definition. |
| AssetBundle | A Unity-built container for engine assets. It is different from this project's custom KAC2 file. |
| Bind pose | A matrix defining the relationship between mesh space and a bone's rest space for skinning. |
| Bone / transform | A named node with position, rotation and scale. Not every retained transform necessarily influences vertices. |
| Carcass | The separate native wreck/death presentation referenced by unit death data. |
| Commander | The game's player/faction loadout and simulation owner, not just a visible carrier model. |
| Entity definition | Named attributes registered as a type from which game entities obtain behavior/data. |
| Hook | An inserted call or interception at a selected native managed-code boundary. |
| IL | Intermediate language instructions in a managed .NET/Mono assembly; Cecil edits these before execution here. |
| LOD | Level of detail: a different rendering representation selected according to native thresholds. |
| Mono | The managed runtime used by this game's Unity build. |
| Prefab | A reusable Unity object hierarchy and its components, distinct from the mesh alone. |
| Rig / skinning | The hierarchy and vertex bindings that let animated transforms deform geometry. |
| Runtime mod | A change applied while the game loads/runs, rather than rewriting its original files on disk. |
| SDK | A documented set of interfaces, formats and tools for third-party authors; proposed here, not delivered by the current mod. |
| Shader | GPU rendering code used by a material; textures alone cannot replace a missing/destroyed shader. |
| Simulation | Gameplay state and rules, including health, research, commands and weapon operation. |
| Presentation | The Unity-side model, animation, UI, effects and sound representing gameplay state. |
| Status effect / buff | Native data and processing that modify unit behavior or attributes according to defined conditions/selectors. |
